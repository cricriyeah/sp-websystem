# Project Audit — sistema-pescadeportiva — 2026-08-12

## Executive Summary
Django 6 + DRF backend / Next.js 16 + React 19 frontend, monorepo, commerce archetype (Stripe checkout for pesca-deportiva tour bookings, PCI-DSS SAQ-A scope). Core payment logic (idempotent PaymentIntent creation, webhook-as-source-of-truth, atomic refund/dispute handling) is well built and matches its own documentation. Biggest risk is operational, not code quality: production has an SSL-redirect misconfiguration that will loop forever behind Render's proxy, and 91 files of core business logic (the entire `finance` and `notifications` apps, `payments/services.py`) sit uncommitted in the working tree with no CI to catch a regression before it reaches customers paying with real cards.

## Architectural Mental Model
This is a single-tenant operational tool, not a multi-tenant SaaS — despite `commerce` archetype and `enterprise-saas`-style reviewers being available, none of that applies here. The system correctly centers on one invariant: `Reserva.clean()` is the single rule engine (cupo diario, ventana de salida, deslinde, 48h de cambio) and every entry point (API, admin, shell) is documented to call `full_clean()` before save — this is the right pattern for a small team and avoids the classic "same rule implemented twice, drifts apart" bug. Money math lives in one file (`apps/payments/pricing.py`), uses `Decimal` with explicit quantization, and is server-computed only — the frontend never sends a total. The webhook is correctly treated as the only source of payment truth, with `select_for_update` + `transaction.atomic` for double-delivery safety and `idempotency_key` on both PaymentIntent creation and refunds. Where the system is weak is everywhere outside that core: no CI runs the 125 tests that protect it, no error tracker would tell anyone if the webhook silently started failing, and the deploy config (cron schedules, proxy headers) lives outside the repo, undocumented and unreviewable.

## Things That Look Bad But Are Actually Fine
- **`REST_FRAMEWORK.DEFAULT_PERMISSION_CLASSES = ['AllowAny']`** (`base.py:40`) — looks like the whole API is wide open, but this is intentional: the public web checkout never authenticates by design (`backend/CLAUDE.md`), and every write is gated by object-level checks instead (`checkout_id` UUID match in `payments/views.py:47`, server-computed pricing). Django admin is a fully separate, session-authenticated surface.
- **No visible CSRF token handling in `frontend/src/lib/api.ts`** — looks broken for a Django backend with `CsrfViewMiddleware` active, but DRF's `APIView.as_view()` wraps `dispatch` in `csrf_exempt` by default; Django's CSRF check never applies to these endpoints. Verified `payments/views.py` and `bookings/views.py` both use `APIView`.
- **`_verificar_monto` logs a mismatch but never rejects the payment** (`backend/apps/payments/services.py`, per `backend/CLAUDE.md`) — looks like a validation bypass, but rejecting here would leave a customer who already paid Stripe with no booking and no refund path; logging for manual review is the correct trade-off for this business.
- **Double panga/capitán assignment not validated** in `Reserva.clean()` — looks like a missing business rule, but `backend/CLAUDE.md` documents this as intentional: the vendedora may deliberately stagger two trips on the same boat.
- **`backend/apps/bookings/models.py` at 396 lines holding 4 models + the day-quota engine** — large by line count, but it's the single authoritative rule engine the codebase explicitly avoids duplicating elsewhere (`full_clean()` must be called from every entry point). Splitting it would scatter one cohesive set of business rules across files for no benefit.
- **`frontend/src/components/checkout-view.tsx` at 522 lines** — large for one component, but it's a single multi-step wizard with shared local state; the steps are tightly coupled by design (currency choice affects amenity pricing affects total affects Stripe amount). Extracting sub-components without a state-management pass would just move complexity, not remove it.

## Open Questions for the Maintainer
