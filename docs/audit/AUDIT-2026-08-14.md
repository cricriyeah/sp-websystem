# Project Audit — sistema-pescadeportiva — 2026-08-14 (re-audit)

Prior audit: `docs/audit/AUDIT-2026-08-12.md` (F-01..F-16). This run verifies the 12
claimed fixes against current code, does not re-report what actually holds, and
focuses on the driving question: **what breaks or bites on first contact with
production** (real Stripe keys, real Supabase Postgres). Findings continue the
numbering at F-17.

## Executive Summary

12 of 16 prior findings verified fixed in code (see "Verification of prior
findings"). The remaining 4 (F-06, F-08, F-14, F-16) are unchanged and correctly
rated. This run found **2 new Critical issues that will stop the first production
deploy or corrupt data under real concurrency**, neither of which existed as a
concern in the previous audit because sqlite (single-writer, serialized) and an
empty database (no health-check dependency ever exercised) both hide them: (1)
`render.yaml`'s `healthCheckPath: /api/tarifa/` returns 503 until a human
manually creates the `Tarifa` singleton row — Render cancels a deploy whose
health check never passes, so the first deploy is guaranteed to fail unless this
is sequenced correctly; (2) the day-quota check (`validar_cupo_diario`) that
prevents overbooking a boat past its physical capacity has no row-level lock
across the reservations it counts — only the single reserva being paid is
locked — so two customers paying for the same day's last two slots at the same
moment, both processed by real concurrent Postgres transactions, can both pass
the check and both get confirmed, something the sqlite-backed test suite cannot
reproduce and does not test for. 139 backend tests pass locally; the whole suite
has never run against Postgres.

## Go-Live Checklist (synthesizes F-17, F-18, F-21, F-22, F-23)

Sequenced for a first real deploy with live Stripe keys:

1. **Before any deploy**: fix F-17 (decouple health check from `Tarifa` existence) — otherwise the deploy is cancelled by Render automatically and nothing below is reachable.
2. **Env vars** (F-22): confirm all of `DJANGO_SECRET_KEY`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`, `DB_HOST`, `DJANGO_ALLOWED_HOSTS`, `CORS_ALLOWED_ORIGINS`, `STRIPE_SECRET_KEY`, `STRIPE_PUBLISHABLE_KEY`, `STRIPE_WEBHOOK_SECRET` are set in the Render dashboard with **live**-mode Stripe values, not test-mode (`sk_live_...`/`pk_live_...`/the webhook secret from the live-mode endpoint, not the CLI-forwarded test one referenced in `backend/.env.example:9`).
3. **Stripe dashboard**: register the production webhook endpoint (`https://<domain>/api/stripe/webhook/`) for live mode explicitly — it is a separate registration from any test-mode endpoint already configured, and `STRIPE_WEBHOOK_SECRET` differs per endpoint.
4. **Deploy**, then immediately (F-18): Render Shell → `createsuperuser` → log into `/admin/` → create the `Tarifa` row → Shell → `setup_roles` → create vendedora accounts.
5. **Frontend** (F-23): confirm `NEXT_PUBLIC_API_URL` on the hosting platform points at the real backend domain *before* triggering the production build (it's baked in, not late-bound).
6. **Verify** `X-Forwarded-Proto` behavior against the live domain (already flagged as an open question in `docs/threat-models/TM-payments.md`'s "Huecos abiertos" — do this now, not later).
7. Do a single real low-amount live-mode charge end-to-end before opening to real customers, watching Render's logs directly (no alerting exists yet — F-06).

## Things That Look Bad But Are Actually Fine (this run)

- **`_intent_de` (`apps/payments/views.py:116-140`) doesn't handle a `canceled` Stripe intent status explicitly** — looks like a gap in the `INTENT_REUTILIZABLE`/`INTENT_YA_COBRANDO` set logic, but tracing the control flow: if a fetched intent's status matches neither set, execution falls through both `if` blocks and reaches the final `return stripe.PaymentIntent.create(...)`, correctly creating a fresh intent. No bug.
- **`RESEND_BCC`/`WHATSAPP_*` defaulting to empty strings/lists in `base.py`** — looks like unfinished config, but `backend/CLAUDE.md` and the code both confirm each channel is opt-in per env var and a missing one is a documented no-op, not a crash. Verified no code path treats an empty `WHATSAPP_TOKEN` as an error.
- **Migration `0011_backfill_fechas_de_dinero.py` uses `RunPython` with plain Django ORM `.update(F(...))` calls, no raw SQL** — the only data migration in the repo, and it's backend-agnostic by construction; no sqlite-specific syntax to break against Postgres.
- **`TruncDate` used for daily grouping in `apps/finance/services.py:94`** — flagged as unverified rather than broken (see F-20): Django has handled per-backend timezone-aware date truncation consistently since well before 6.0, and nothing in the code overrides that. Not asserting a bug without a Postgres test run to confirm either way — that's exactly what F-20 fixes.
- **`stripe.api_version` unpinned is Medium, not Critical** — Stripe's own versioning practice is that breaking changes are opt-in via version pinning; an account's default version only changes when a human changes it in the dashboard, which is a controllable, documented event, not a silent vendor-side push. Still worth pinning (F-21), but not an imminent-failure item the way F-17/F-19 are.
