### Reporte de revisión del commit `96d8fe2` (Tarea 04: Apartado de Hospedaje)

Revisión contra el spec `docs/superpowers/specs/2026-10-12-apartado-temporal-cupo-design.md` (§4.1, §4.2 y §7):

#### 1. Caída no controlada (`TypeError`) en `habitaciones_apartadas` ante valores nulos
* **Archivo:línea**: `backend/apps/bookings/cupo/apartado.py:162-167`
* **Defecto**:
  ```python
  try:
      o_ini = date.fromisoformat(ini_val) if isinstance(ini_val, str) else ini_val
      o_fin = date.fromisoformat(fin_val) if isinstance(fin_val, str) else fin_val
  except (ValueError, TypeError):
      continue
  if o_ini < hasta and o_fin > desde:
  ```
  Si `ini_val` o `fin_val` es `None` (o un tipo numérico/booleano en un JSON corrupto/incompleto), `isinstance(..., str)` es `False`, asignando `o_ini = None` sin disparar el bloque `except`. Inmediatamente después, en la línea 167 (fuera del `try/except`), se ejecuta `o_ini < hasta`. En Python 3, `None < date` lanza un `TypeError: '<' not supported between instances of 'NoneType' and 'datetime.date'` no capturado, rompiendo toda la consulta de disponibilidad en lugar de descartar la entrada.

#### 2. Omisión de restricción de órdenes cruza-empresa en `construir_retrato_hospedaje` (Contradicción con Spec §2)
* **Archivo:línea**: `backend/apps/bookings/cupo/apartado.py:198-200`
* **Defecto**: El spec (§2) define explícitamente fuera de alcance v1 las reservas pertenecientes a órdenes cruza-empresa (`Orden` / `orden_id`), las cuales no deben apartar inventario. Mientras que `construir_retrato_paquete` (línea 249) sí comprueba `if getattr(reserva, 'orden_id', None) is not None: return ...`, `construir_retrato_hospedaje` no valida `reserva.orden_id`. Una reserva directa de hospedaje asociada a una orden cruza-empresa generará apartados virtuales en contravención con la especificación.

#### 3. Tenancy y selección rota en paquetes con hospedaje (`construir_retrato_paquete`)
* **Archivo:línea**: `backend/apps/bookings/cupo/apartado.py:282-290`
* **Defecto**:
  ```python
  elegidos = elegir_habitaciones(
      servicio=servicio,
      desde=desde,
      hasta=hasta,
      personas=personas,
      empresa=reserva.empresa,
      excluir_pk=reserva.pk,
  )
  ```
  Se pasa `empresa=reserva.empresa` al seleccionar habitaciones de cada componente. Si el paquete incluye un hospedaje de otra empresa (paquete cruza-empresa sin `orden_id`), `obtener_recursos_con_ocupaciones` busca recursos con `empresa=reserva.empresa` y `servicio=servicio`. Como los recursos pertenecen a `servicio.empresa`, la consulta siempre regresa `[]`, lanzando un falso `SinCupoError`.
  Asimismo, no se valida `paquete.es_cruza_empresa` ni `servicio.empresa_id == reserva.empresa_id` antes de procesar componentes (violando Spec §2 y §4.1).

#### 4. Riesgo de carrera / aislamiento de candado en `_asignar_cupo_hospedaje`
* **Archivo:línea**: `backend/apps/bookings/cupo/confirmacion.py:75-76`
* **Defecto**:
  ```python
  for recurso in recursos_candidatos:
      bloquear_recurso(reserva.empresa_id, recurso.pk)
  ```
  `bloquear_recurso` toma el candado a nivel de base de datos como `pg_advisory_xact_lock(empresa_id, clave)`. Se utiliza `reserva.empresa_id` en lugar de la empresa del recurso (`recurso.empresa_id` o `servicio.empresa_id`). Si difirieran (en componentes delegados), el candado se tomaría bajo una empresa distinta a la que consultan los clientes directos de ese hotel, permitiendo condiciones de carrera sobre el mismo recurso físico.
