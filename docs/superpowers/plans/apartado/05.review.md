### Reporte de revisión del commit `2945d96` (Tarea 05: Crear-Pago, Bloques A/B/C y Contrato de Errores)

Revisión contra el spec `docs/superpowers/specs/2026-10-12-apartado-temporal-cupo-design.md` (§4.3 y pruebas asociadas en §5):

---

#### 1. Fuga de Tenancy / RLS en `_bloque_b` (`_tiene_cupo_fisico` fuera de scope)
* **Archivo:línea**: `backend/apps/payments/views.py:210` y `475-478`
* **Defecto**:
  En `_bloque_b`:
  ```python
  reserva = contexto['reserva']
  if not apartado_activo() or not self._tiene_cupo_fisico(reserva):
      return {'apartado_hasta': None, 'creo_apartado': False}
  ```
  La llamada `self._tiene_cupo_fisico(reserva)` se ejecuta **antes** de abrir `with scope.con_empresa(empresa):` (línea 215). Como el Bloque A ya concluyó, `scope.con_empresa` reseteó `app.current_empresa_id` a `DEFAULT`.
  Dentro de `_tiene_cupo_fisico`:
  ```python
  if reserva.paquete_id and reserva.paquete:
      return reserva.paquete.servicios_asociados.filter(
          servicio__estrategia_cupo__in=['por_recurso_dia', 'por_noche']
      ).exists()
  ```
  `servicios_asociados.filter(...).exists()` ejecuta una consulta SQL sobre `fleet_paqueteservicio` sin contexto de empresa. En PostgreSQL con RLS (rol de aplicación `ci_rls`), las consultas a tablas de tenant sin `app.current_empresa_id` devuelven 0 filas en silencio.
  Por lo tanto, bajo Postgres con RLS, para **cualquier paquete** `_tiene_cupo_fisico` devuelve `False`, omitiendo el Bloque B por completo y dejando la reserva sin apartado. En SQLite esto pasó inadvertido porque no tiene RLS.

#### 2. Contradicción con Spec §4.3 y `except` demasiado amplio: Cobro en curso tratado como 502 con liberación indebida
* **Archivo:línea**: `backend/apps/payments/views.py:426-430`
* **Defecto**:
  El spec (§4.3, Bloque C) exige explícitamente:
  > *«Lo mismo si Stripe rechaza un update/create porque el intent pasó a processing o succeeded en ese instante: ese error se trata como PagoEnCurso (responde pago_en_curso), nunca como un 502 con liberación.»*
  Sin embargo, en `_bloque_c`:
  ```python
  except stripe.StripeError:
      logger.exception('Stripe fallo al preparar el pago de la reserva %s', reserva.pk)
      if apartado_info.get('creo_apartado') and apartado_info.get('apartado_hasta'):
          self._liberar_apartado_si_procede(empresa, reserva.pk, apartado_info['apartado_hasta'])
      return Response({'detail': 'No se pudo iniciar el pago. Intenta de nuevo.'}, status=502)
  ```
  Al atrapar indiscriminadamente cualquier `stripe.StripeError`, si Stripe rechaza `update` o `create` con un `InvalidRequestError` debido a que el intent pasó a `processing` o `succeeded` concurrentemente, el código lo clasifica como falla de pasarela 502 y **libera el apartado del cliente que ya está pagando**, violando la regla del spec.

#### 3. Carrera / Omisión de validación de `reserva.estado` tras `refresh_from_db` en Bloque C
* **Archivo:línea**: `backend/apps/payments/views.py:406-447`
* **Defecto**:
  En Bloque C se recarga la reserva (`reserva.refresh_from_db()`), pero **nunca se verifica `if reserva.estado != Reserva.Estado.PENDIENTE_PAGO:`** (como sí se hace en Bloque A:107 y Bloque B:227).
  Si entre el commit del Bloque B y el inicio del Bloque C el webhook de Stripe marcó la reserva como `PAGADA` o una acción concurrente la marcó como `CANCELADA`, Bloque C no responde `409 ya_no_pendiente`, sino que continúa hacia Stripe y sobreescribe campos en base de datos (`reserva.save(update_fields=[...])`).

#### 4. Tenancy defensivo: Falta filtro de `empresa` en `_liberar_apartado_si_procede`
* **Archivo:línea**: `backend/apps/payments/views.py:464-467`
* **Defecto**:
  ```python
  Reserva.objects.filter(
      pk=reserva_id,
      apartado_hasta=apartado_hasta_escrito,
  ).update(apartado_hasta=None, apartado_demanda=None)
  ```
  La consulta filtra únicamente por `pk` y `apartado_hasta`, omitiendo `empresa=empresa`. En entornos sin RLS (SQLite local y tests), no aísla la fila a la empresa de la petición, violando la convención del proyecto (`CLAUDE.md:97-98`).
