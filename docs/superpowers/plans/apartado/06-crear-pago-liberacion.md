# Tarea 06: `crear-pago` libera con seguridad; editar la reserva borra el apartado

Lee del spec: §4.3 (Bloque C y sus reglas de liberación, «Editar la reserva sin pasar por crear-pago», tabla de errores con el 503 `reintentar`), §4.6 solo para el contrato.

## Qué hacer
1. **Bloque C** de `CrearPagoView`: si Stripe falla (502/timeout) y ESTA llamada creó el apartado (antes no había uno vigente), libéralo con escritura condicional (`Reserva.objects.filter(pk=..., apartado_hasta=<valor que escribió esta llamada>).update(apartado_hasta=None, apartado_demanda=None)`), para no borrar el que otra llamada concurrente haya renovado. Si esta llamada solo RENOVÓ un apartado existente, no se libera ni se restaura nada. Si `PagoEnCurso` se lanza en el Bloque C, o Stripe rechaza un `update`/`create` porque el intent pasó a `processing`/`succeeded` en ese instante, responde `pago_en_curso` y NO toques el apartado. El Bloque C vuelve a consultar el intent (hoy lo hace `_intent_de`); el Bloque A solo lo usa para la salida temprana.
2. **Candado no obtenido a tiempo**: en el Bloque B un `lock_timeout` agotado (error de Postgres `55P03`, `LockNotAvailable`) responde `503 {"detail": "...", "codigo": "reintentar"}`, no un 500. (Deadlock `40P01`: reintento, ya definido en la tarea 05.)
3. **Editar la reserva sin pasar por `crear-pago`**: `ReservaCheckoutView` es un upsert por `checkout_id` (`backend/apps/bookings/views.py`, `_pendiente_de`, y `serializers.py`). Cuando el upsert cambia un campo relevante para el cupo (fecha, hora, numero_personas, servicio, paquete, fecha_salida, personas_por_servicio) debe BORRAR `apartado_hasta` y `apartado_demanda`. `apartado_hasta` y `apartado_demanda` NO se agregan a los campos escribibles del serializador público (revisa que `ReservaCheckoutSerializer` use una lista explícita y confírmalo con una prueba).

## Pruebas (archivos nuevos `backend/apps/payments/tests_apartado_liberacion.py` y `backend/apps/bookings/tests_apartado_edicion.py`)
Stripe falla tras crear el apartado ⇒ se libera (y la liberación es condicional: simula que otra llamada lo renovó y comprueba que NO se borra); Stripe falla tras solo renovar ⇒ el apartado se conserva; `PagoEnCurso` en el Bloque C y la carrera A→C (el intent pasa a `processing` entre la lectura y el `update`) ⇒ `pago_en_curso` sin liberar; `lock_timeout` ⇒ 503 `reintentar` (simula la excepción de la base de datos); cambiar fecha, personas, servicio, paquete o fecha_salida por `POST /reservas/` borra el apartado y cambiar solo el nombre del cliente NO lo borra; `apartado_hasta` no es escribible por la API pública.
