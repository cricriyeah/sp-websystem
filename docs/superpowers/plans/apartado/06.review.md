### Reporte de revisión: commit `b800225` (Tarea 06: Bloque C, liberación segura, cobro en curso y edición)

Revisión contra el spec `docs/superpowers/specs/2026-10-12-apartado-temporal-cupo-design.md` (§4.3, §5):

---

#### 1. Tenancy / RLS: `_tiene_cupo_fisico` ejecutado fuera de `con_empresa`
* **Archivo:línea**: `backend/apps/payments/views.py:210` (y definición en `512-522`)
* **Defecto**: En `_bloque_b`:
  ```python
  if not apartado_activo() or not self._tiene_cupo_fisico(reserva):
  ```
  Se evalúa antes de entrar al bloque `with scope.con_empresa(empresa):` (línea 215). En PostgreSQL con RLS (`ci_rls`), la consulta `reserva.paquete.servicios_asociados.filter(...).exists()` se ejecuta con `app.current_empresa_id = DEFAULT` y devuelve 0 filas silenciosamente. Esto causa que ningún paquete tome apartado temporal bajo Postgres con RLS.

---

#### 2. Carrera / Omisión de validación de `reserva.estado` tras `refresh_from_db` en Bloque C
* **Archivo:línea**: `backend/apps/payments/views.py:423-470`
* **Defecto**: Al inicio de `_bloque_c` se recarga la reserva (`reserva.refresh_from_db()`), pero **nunca se verifica `if reserva.estado != Reserva.Estado.PENDIENTE_PAGO:`** (a diferencia de Bloque A:107 y Bloque B:227). Si entre el commit del Bloque B y el inicio del Bloque C la reserva fue pagada por webhook o cancelada, Bloque C no responde `409 ya_no_pendiente`: contacta a Stripe, sobreescribe los campos de la reserva en BD (`reserva.save(update_fields=[...])`) y devuelve 200 con `client_secret` para volver a cobrar, violando Spec §4.3.

---

#### 3. Nombre inventado y coincidencia demasiado amplia en `_es_rechazo_por_pago_en_curso`
* **Archivo:línea**: `backend/apps/payments/views.py:498-500`
* **Defecto**:
  ```python
  msg = str(exc).lower()
  if any(term in msg for term in ('processing', 'succeeded', 'ya cobrando')):
      return True
  ```
  1. **Nombre inventado**: `'ya cobrando'` es una cadena inventada en español que la API en inglés de Stripe jamás devuelve (confusión con el set de Python `INTENT_YA_COBRANDO`).
  2. **Except / Coincidencia demasiado amplia**: El chequeo `'processing' in msg` sobre cualquier `stripe.StripeError` atrapa errores genéricos de pasarela de Stripe como `"An error occurred while processing your request"` (mensaje estándar de `stripe.APIError` 500). Esto provoca que caídas del servicio de Stripe se clasifiquen erróneamente como `409 {"codigo": "pago_en_curso"}` en vez de responder 502 y liberar condicionalmente el apartado creado.

---

#### 4. Prueba que no prueba lo que declara: `test_cambiar_personas_por_servicio_en_paquete_borra_apartado`
* **Archivo:línea**: `backend/apps/bookings/tests_apartado_edicion.py:322-372`
* **Defecto**: El paquete configurado tiene un único servicio operativo. Al cambiar `personas_por_servicio` de 2 a 3 en el payload, el serializador (`_derivar_de_paquete`) recalcula y muta también `numero_personas` a 3. Como consecuencia, la condición de borrado de apartado se cumple por el cambio en `numero_personas` (`instance.numero_personas != 3`), y no aísla ni prueba que el cambio en `personas_por_servicio` por sí solo borre el apartado (si se retirara `personas_por_servicio` de `campos_relevantes_cupo`, el test seguiría pasando).
